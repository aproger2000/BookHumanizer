# Редактор глав

Простой сервис для редакторской правки глав книги, черновик которых
сделан с помощью ИИ. Алгоритм не «маскирует» текст под конкретный
детектор, а выполняет обычную литературную правку: убирает однообразный
ритм предложений, штампованные связки, канцелярит и общие места,
добавляет конкретики — при этом сюжет, герои и голос автора сохраняются
без изменений. Итоговый текст стоит всегда перечитывать самому перед
публикацией.

## Стек

- Backend: Flask (Python, один файл `app.py`), вызывает Claude API напрямую по HTTP
- Frontend: одна статическая HTML-страница (без сборки)
- Деплой: Render (Web Service), один процесс на весь сервис

## Локальный запуск

```bash
python3 -m venv .venv
source .venv/bin/activate
pip install -r requirements.txt

cp .env.example .env
# впишите свой ключ в .env:
# ANTHROPIC_API_KEY=sk-ant-...

export $(grep -v '^#' .env | xargs)   # или используйте python-dotenv
python app.py
```

Откройте http://localhost:8000 — там форма для вставки текста главы или
загрузки файла .txt/.md/.docx. Обработка идёт потоково (SSE): в интерфейсе
виден живой прогресс-бар по мере генерации текста моделью, а не просто
спиннер без обратной связи.

## Подсветка правок

В окне «После правки» все изменённые места подсвечены жёлтым — word-level
diff (в браузере, без сторонних библиотек) сравнивает исходный и
обработанный текст и оборачивает изменённые слова в `<mark>`. Подсветку
можно выключить галочкой «Подсветка правок» рядом с кнопками
«Скопировать»/«Скачать» — текст при этом не пересчитывается, просто
убирается фон. Копирование и скачивание всегда берут чистый текст без
разметки.

Абзацы исходного и обработанного текста выравниваются не по номеру по
порядку, а по смысловому сходству (по пересечению слов) — упрощённый
Needleman-Wunsch поверх абзацев. Это специально сделано так, потому что
сама правка регулярно меняет количество абзацев (разбивает длинный абзац
на два, выносит реплику в отдельную строку и т.п.) — раньше подсветка
требовала точного совпадения числа абзацев и при любом расхождении молча
показывала текст вообще без подсветки, хотя правки в нём были (это и
есть баг, исправленный в v1.10.0). Теперь подсветка находит для каждого
нового абзаца наиболее похожий старый (или помечает его целиком новым,
если похожего не нашлось) и работает даже при таких структурных правках.

## Выбор стиля

Кроме глубины правки, в интерфейсе можно выбрать регистр подачи:

- **Нейтральный** — обычная редактура (по умолчанию).
- **Динамичная фантастика (в духе Головачёва / Лукьяненко)** — та же
  правка, но с уклоном в быстрый, кинематографичный темп жанровой
  фантастики: короткие резкие фразы в динамике, живые ироничные диалоги,
  уверенный драйв повествования.

Это смена регистра/интонации, а не копирование текста этих авторов —
конкретный стиль изложения не защищён авторским правом, но их фирменные
придумки (термины, персонажи, вселенные) — защищены. Поэтому в промпте
(пресет `dynamic_scifi` в `STYLE_PRESETS`, `app.py`) есть прямой запрет
заимствовать конкретную терминологию, персонажей или формулировки из их
книг — берётся только общее ощущение темпа, тона и подачи, применённое к
сюжету и тексту самого пользователя.

## Ритм предложений и лексика

В системном промпте (`SYSTEM_PROMPT` в `app.py`) есть отдельные указания
на ритм и словарь:

- **Ритм** — длина предложений должна колебаться не механически через
  одно, а с ощутимым перепадом: короткое, рубленое предложение, затем
  заметно более длинное (примерно в полтора раза длиннее — свободное
  ощущение золотого сечения, не формула для расчёта), затем снова
  сжатие. Три и более предложений подряд одинаковой длины и формы —
  повод разбить этот ряд.
- **Лексика** — предпочтение отдаётся словам, которые человек
  действительно употребил бы в разговоре, а не книжным или официальным
  синонимам: простая, повседневная, местами просторечная лексика вместо
  канцелярита и излишне «литературных» оборотов, если это не противоречит
  голосу персонажа или рассказчика.

Это указания по ремеслу, не количественная формула для самопроверки —
модель не обязана вычислять пропорции, только ориентироваться на них при
редактуре.

## Форматирование

Три пунктуационных правила применяются гарантированно, поверх того, что
вернула модель — они прописаны и в промпте (модель старается следовать им
сама), и дополнительно принудительно приводятся к нужному виду в коде
(`_normalize_output_formatting` в `app.py`), чтобы не зависеть от того,
насколько аккуратно модель их соблюла:

- длинное тире «—» заменяется на короткий дефис «-» везде, включая тире
  перед репликами в диалогах;
- между абзацами оставляется ровно одна пустая строка, не больше (раньше
  из-за того, что сервис стал дословно сохранять пробелы модели, иногда
  проскакивали лишние пустые строки — теперь это исправлено);
- строка-отбивка между сценами вида «---» заменяется на «*************».

## Что сервис намеренно не делает

Помимо количественных порогов из чек-листа (см. раздел выше), сервис не
берёт в работу требования вида «не менее 40% предложений короткие или
длинные», «не менее N авторских слов на 500 знаков» или «одно авторское
отступление на каждые 1000 знаков». Это не формулировки ремесла, а
статистические профили — ровно то, на что ориентируются алгоритмы
детекции ИИ-текста, и то же самое, что раздел «самопроверка» просил
изначальный ТЗ. Плотность образных выражений и лирических отступлений
уже покрыта качественными пунктами промпта и чек-листа (`fresh_imagery`,
рубрика про интериорность), но без обязательного счётчика на каждые N
знаков — это превратило бы редактуру в подгонку под метрику, а не в
работу с конкретным текстом.

## Деплой на Render

1. Загрузите этот проект в свой репозиторий на GitHub (см. ниже).
2. На https://dashboard.render.com нажмите **New → Blueprint** и укажите
   ваш репозиторий — Render найдёт `render.yaml` и настроит сервис
   автоматически (план `free`).
   - Либо вручную: **New → Web Service**, подключите репозиторий,
     Build Command — `pip install -r requirements.txt`, Start Command —
     `gunicorn app:app --bind 0.0.0.0:$PORT --timeout 340`.
3. В настройках сервиса (**Environment**) добавьте переменную
   `ANTHROPIC_API_KEY` со своим ключом с https://console.anthropic.com.
   Переменная `ANTHROPIC_MODEL` уже задана в `render.yaml`, но её можно
   поменять на любую доступную вам модель Claude.
4. Дождитесь деплоя — Render выдаст публичный URL вида
   `https://book-chapter-editor.onrender.com`.

Бесплатный план Render «засыпает» сервис после периода бездействия —
первый запрос после паузы может занять 30–60 секунд.

## Модель и лимит вывода

По умолчанию сервис использует `claude-sonnet-5` (переменная
`ANTHROPIC_MODEL`) с лимитом вывода `MAX_OUTPUT_TOKENS = 64000` (в
`app.py`). Раньше по умолчанию стояла устаревшая `claude-sonnet-4-5-...`
с лимитом 8192 токенов — для длинных глав с расширенным чек-листом этого
не хватало, ответ модели обрывался на середине, и сервис падал с ошибкой
«The model did not return valid JSON.» Если снова увидите эту ошибку —
скорее всего, не хватает `MAX_OUTPUT_TOKENS` для конкретной главы;
сервис теперь также отдельно распознаёт обрыв по лимиту токенов
(`stop_reason: "max_tokens"`) и в этом случае показывает понятную
ошибку с советом сократить главу или снизить глубину правки, а не
голое «невалидный JSON».

## Версия

Номер версии живёт в константе `APP_VERSION` в начале `app.py` и
отображается в подвале страницы (например, «v1.2.0») — это позволяет
сразу увидеть на живом сайте, подхватил ли Render последний деплой.
Также его отдаёт `GET /api/health` в поле `version`.

**При каждом изменении, которое уходит в деплой, увеличивайте
`APP_VERSION`** (например, 1.2.0 → 1.2.1 для мелкого фикса, → 1.3.0 для
новой возможности).

## Чек-лист после правки

После каждой обработки сервис показывает чек-лист по итогам правки —
модель честно (в промпте явно указано не ставить везде «зачёт») оценивает
результат по двенадцати пунктам ремесленного качества: разнообразие
синтаксиса, смесь длины предложений, отсутствие штампов, уместные образы,
неровный ритм, начало абзацев не с подлежащего, живые переходы, живые
диалоги (паузы и действия вместо одних «сказал/ответил»), отсутствие
«раскадровочной» подачи действий, звучание при чтении вслух, сохранность
сюжета и полнота охвата — что правка коснулась вообще всех абзацев, ни
один не оставлен нетронутым (промпт прямо требует хотя бы лёгкую правку
каждого абзаца, даже если он и так хорош). Тринадцатый пункт (объём
текста в пределах ±10% от оригинала) сервис считает сам, а не спрашивает
у модели.

В чек-лист по-прежнему намеренно не включены количественные пороги из
технического задания (доля предложений с подлежащего, коэффициент
вариации длины, явный запрет на предложения в 8–12 слов как «характерные
для нейросетей», процент уникальных слов и т.п.) — это статистические
признаки, на которые ориентируются детекторы ИИ-текста. Не включено и
добавление переживаний персонажа, «не связанных с сюжетом» — это уже
выдумывание контента, а не стилистическая правка. Сервис остаётся
инструментом литературной правки, а не инструментом обхода конкретных
детекторов;
итоговый текст всегда стоит вычитывать самому. Список пунктов чек-листа
живёт в `CHECKLIST_ITEMS` в `app.py`.

### Фикс v1.9.1 — «правка» без единого изменения

Была ошибка: при интенсивности «Лёгкая» модель иногда возвращала главу
вообще без изменений (или почти без них), хотя чек-лист требует полноты
охвата. Причина — формулировка подсказки для лёгкой интенсивности
(«меняйте как можно меньше») напрямую противоречила требованию «каждый
абзац должен быть тронут». Исправлено тремя правками:

1. Подсказка для «Лёгкой» интенсивности переформулирована: она теперь
   явно разделяет *насколько* меняется абзац (минимально) и *меняется
   ли он вообще* (да, всегда) — раньше эти два смысла сливались в одну
   фразу, и модель делала вывод, что абзац можно вообще не трогать.
2. Требование полноты охвата в системном промпте усилено: «это жёсткое
   требование, а не пожелание» — прямо запрещает пропускать абзацы даже
   при «минимальных» правках.
3. Добавлена серверная подстраховка: если модель всё же вернула текст,
   идентичный оригиналу, сервис не показывает его как «успешную» правку,
   а сразу выдаёт понятную ошибку с советом повторить попытку или выбрать
   более сильную интенсивность («Тщательная») либо другой стиль.

## Ограничения

- Обрабатывает главу целиком за один запрос (до ~60 000 символов);
  более длинные главы стоит делить на части.
- Требует собственный ключ Anthropic API (платный по использованию,
  см. https://console.anthropic.com).
